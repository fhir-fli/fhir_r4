# fhir_r4_db

## [Unreleased]

- **`:in` / `:not-in` refuse a ValueSet whose compose they cannot evaluate, and honour `exclude.concept`.** `include.filter`, `include.valueSet` and the same on `exclude` are not implemented; the codes used to be taken from the parts that are and the rest ignored, so the search answered against a different set than the one defined. Now `UnsupportedValueSetCompose` is thrown, for the caller to refuse (fhirant answers 400 not-supported); `exclude.concept` lists, which were ignored, take their codes out (fhirant REVIEW-2026-09-06 finding 24).
- **The general search path no longer guesses a parameter's type from its values, and no longer reads `:missing` off the end of a value.** A parameter this build has no definition for is skipped, as the SQL-paged path already did (R4B 3.1.1.3: unknown parameters are ignored; a strict client's refusal is the server's); a chained key goes to the reference branch. The ~250-line branch that inferred date, quantity, token, uri or reference from a pipe, a leading digit or an http prefix, and the branch that treated a value ending in `:missing` as the modifier, are deleted (fhirant REVIEW-2026-09-06 finding 26).

- **`getResources(type, ids)` reads a set of resources in `IN (...)` chunks**, in id order, one statement per 500 ids where a caller looped over `getResource` (fhirant's `_include` read every target one by one; REVIEW-2026-09-06 finding 39).

- **`searchIds` returns the matching ids and reads nothing else; a long `_id` list takes the set path.** The same conditions as `search` without the page or the hydration, for a caller that wants the set (fhirant's `_filter` read every matching resource per leaf, and the whole type for `not(...)`; REVIEW-2026-09-06 finding 38). A repetition of `_id` with more than `maxIdListInSql` (500) comma-separated values leaves the SQL path, where each value was one bound `id = ?` in an OR chain, for the set path, which intersects the Dart set with the other conditions and pages the sorted ids before reading any resource; measured 2026-09-08 with a 40,000-value list on an in-memory store: the SQL path threw `Stack Overflow` building the OR expression (387 ms), the set path answers the same two matches in 187 ms. On that path the `_id` values are now checked against the table first (`IN (...)` chunks of 500): absent ids used to count as matches, so a list of them filled the sorted page with ids no resource has and the page came back empty while the total said otherwise.

- **History is paged and counted in SQL; one version is read by key.** `getHistory(type, id, since:, at:, count:, offset:)` cuts the page in the query and `countHistory` gives the total; `getVersion(type, id, versionId)` reads one row by the primary key and returns its `HistoryEntry` (a tombstone with `deleted` set). fhirant read and parsed a resource's whole history to page it, and every version to find one (REVIEW-2026-09-06 finding 36).

- **A one-key `_sort` walks the key's covering index when the filter is dense at the front of the order.** The grouped LEFT JOIN sorted the whole filtered set: `Observation?status=final&_sort=-date` (813k of 813.5k) took 2.5 s on 929k MIMIC resources before schema 10 and 1.0 s after it. Now, for a single sort key, the first 200 rows of the key's index in sort order are read with the filter as a column; when a quarter or more pass, the page is taken by walking that index with each part as an EXISTS probe, each row kept only as its resource's earliest in the direction (a NOT EXISTS on the same table, ties on rowid; string keys whole-value rows, token keys coded rows, as the join already did), and the resources with no value for the key appended from the resources table when the page runs past the last valued one (R4B 3.1.1.5.1: "sorts last"). Otherwise the join stays: the 48,554 records of one patient are 5 % of the type but sit in one band of dates, and a walk from the newest date read most of the type to reach them (2.3 s in §4.5), which the front sample sees and the join answers in 0.3 s. A bare `_sort` always walks. Measured 2026-09-07 through `FhirAntDb.search` (fhirant REVIEW-2026-09-06 §4.7): `status=final&_sort=-date` 1,004 → 33 ms warm; the patient sorts unchanged. `preferSortWalk` (test hook) forces either shape; `search_sort_test.dart` runs every case as the sizes choose, as the walk, and as the join, against the general path.

- **A single range parameter is paged by size; `_lastUpdated` is one range per prefix.** After schema 10, `SELECT DISTINCT id … ORDER BY id LIMIT` for one parameter left the plan to SQLite: a broad date range came out of the covering index in date order and was sorted whole in a temporary B-tree (`date=ge2150` on 929k MIMIC resources, 25 ms → 764 ms), and `_lastUpdated=ge<future>`, written as an OR of two ranges, was read in key order testing every row (10.4 s to return nothing). Now a single RANGE part (date, `_lastUpdated`, string starts-with) is sized by the existing probe and either fetched whole through its index and paged in Dart (under 100,000 ids) or found by walking the resources table in id order with the part as an EXISTS probe (`_lastUpdated` with its column kept off the index by unary plus, so the walk stays in key order); an EQUALITY part keeps the SQL page, because its covering index already yields id order and stops at the page (a patient's 48,554 Observations fetched whole measured 600 ms against 15). Number and quantity prefixes are ORs over low/high with NULL bounds that no one range serves and keep the SQL page (1.2 s through the probe; a sargable numeric range is a follow-up). `_lastUpdated` prefixes are each one comparison on the millisecond column (`ge` is `>= min(l, h - 1 s + 1 ms)`, `le` is `<= max(l - 1 ms, h - 1 s)`), the same answers as before (`schema10_test.dart`, every prefix). Measured 2026-09-07 through `FhirAntDb.search` (fhirant REVIEW-2026-09-06 §4.7): `_lastUpdated=ge2999` 9.1 s → 4 ms, `date=ge2150` 764 → 48 ms, equality searches unchanged.

- **Schema 10: the index tables lose `search_path` and their key; the value indexes become covering composites; `resources` gains `(resource_type, last_updated)`** (fhirant REVIEW-2026-09-06 §4, measured in its §4.5 on 928,935 MIMIC resources). Every search WHERE carried `(search_name = ? OR search_path LIKE 'T.name' OR search_path LIKE 'T.%.name')`, two alternatives for rows written before schema 5 that no row has had since the schema-7 rebuild; the OR could use no index on `search_name` and cost a string LIKE per candidate row. Gone (28 sites; one `:text` site had the LIKEs alone). `search_path`, a 20–60 byte FHIRPath stored in every row and in every entry of the five-column primary key, was read by nothing after that: the column is dropped and the tables are rowid tables with no declared key (1.16 GB of key indexes on that load). Per table there is now an owner index `(resource_type, id)` for the re-index delete, a covering composite `(resource_type, search_name, <value…>, id)` per value column a search filters or sorts on (sixteen in all), and the contained-row partial index; the fifteen single-column value indexes are dropped. `resources` and `resources_history` get `(resource_type, last_updated)`: the type page and `_lastUpdated` sorted or scanned every row of the type (6.4 s). Measured 2026-09-06 with hand SQL: a token page 100 ms → 6 ms, `_lastUpdated` and the type page 6.4 s → 0 ms, the sort walk for `status=final&_sort=-date` 12.9 s → 0 ms; the production-path A/B (`fhirant_server/tool/review_2026-09-06/schema10_ab.dart`) is recorded beside it. Two rows that differed only in path (Observation.code and Observation.component.code under `combo-code`) are two rows.
- **String starts-with is a range, `_lastUpdated` is on the raw column.** `LIKE 'prefix%'` planned as a read of every string row of the type (SQLite's LIKE optimization needs `case_sensitive_like` or NOCASE, neither set), and treated `%` and `_` in the value as wildcards; `FhirDao.startsWith` writes `>= prefix AND < next(prefix)` (last code point incremented; U+10FFFF dropped; the surrogate range stepped over), which the covering index serves. `_lastUpdated` cast the column to a DateTime in SQL, which no index serves; the comparisons are now on the millisecond column with the one-second resolution moved onto the constants (every prefix tested against instants two hours apart, `schema10_test.dart`).
- **The upgrade re-extracts once.** A database below 7 used to rebuild at 7, again at 9 and would again at 10; the 7 and 9 steps now leave the rebuild to the 10 step. `rebuildSearchIndex` inserts plainly (no key to replace on).
- `_include` names a search parameter, never an element: `Patient:managingOrganization` used to resolve only through the dead LIKE on the path; it is `Patient:organization` (R4B search.html 3.1.1.5.4, "based on search parameters, rather than paths in the resource").
- `:contains` and token `:text` are scans of the parameter's rows by construction and say so in the code.

- **An update keeps the submitted `meta`.** `saveResource` counted the version from the stored meta and then kept that whole meta, so a PUT that added a `meta.profile` or a `meta.tag` lost it, and fhirant's `$meta-add` wrote nothing (probed 2026-09-07). Now the submitted meta is written with the server's `versionId` and `lastUpdated` (R4B http.html "update": the server "SHALL ignore the provided versionId and lastUpdated values" and "SHOULD refrain" from altering the rest), `profile` and `source` as submitted, and the stored `tag` and `security` labels the submission does not repeat kept alongside it, the pattern resource.html 2.26.3.9 describes ("Merge existing and new tags / Replace existing profile tags with new profile tags / Merge existing and new security labels"). `saveResource(mergeTags: false)` writes the labels exactly as submitted, for `$meta-delete`. `saveResources` merges the same way.
- **Writes are one transaction each, and the version is read inside it.** `saveResource` read the stored version, then opened its transaction and wrote version+1, so two concurrent updates of one resource both read n, both wrote n+1, and the second overwrote the first's history row. The read is now inside the transaction, which Drift runs one at a time, so concurrent saves are n+1 and n+2 with both kept (`review_integrity_test.dart`, "two concurrent saves"). `saveResource(resource, ifMatchVersion:)` and `deleteResource(type, id, ifMatchVersion:)` check HTTP `If-Match` there too and throw `VersionConflict` (expected, actual) with nothing written; checked by the caller before the save, a second writer could land between the check and the write. fhirant REVIEW-2026-09-06 finding 30.
- **`saveResources` is atomic and continues the version sequence.** The resource rows and the index rows were two batches, so an indexing failure left the resources stored and unsearchable behind the `false` it returned (finding 27); and it never read the stored meta, so every bulk re-save wrote version 1 and overwrote history version 1 (finding 28). Now one transaction: the stored `meta` of every resource in the batch is read first, one query per type with `json_extract` (no resource parsed), versions continue from it, a resource that appears twice in one batch is two versions with the last copy's index rows, and a failure anywhere rolls back everything. An empty list is still `true`.
- **`deleteResource` removes the contained rows and runs in a transaction.** It deleted the resource's own index rows by primary key and left the rows of anything it contained (`#Medication` under `MedicationRequest/x#m1`) behind as orphans, outside any transaction (finding 29). It now uses the same `_deleteSearchParams` as a save, inside one transaction with the tombstone and the row delete, and the tombstone is `jsonEncode`d rather than interpolated (finding 31).
- **History can be read for a deleted Observation.** `getResourceHistory` parsed the delete's tombstone as the resource type, which throws for any type with a required element (an Observation's `status`): the history of a deleted Observation, and fhirant's 410 check on `GET` of one, failed. New `getHistory(type, id, since:, at:)` returns `HistoryEntry` rows (versionId, lastUpdated, `deleted`, resource or null for a tombstone); `getResourceHistory` keeps returning resources and leaves the tombstones out.
- **`code=|X` matches only codes with no system.** R4B 3.1.1.4.10 (read whole): "`[parameter]=|[code]`: the value of [code] matches a Coding.code or Identifier.value, and the Coding/Identifier has no system property". `_tokenCondition` treated the empty system as absent and matched every system (finding 17); the composite branch already did it right.
- **An absolute versioned reference indexes as type/id/version.** `http://example.org/fhir/Patient/123/_history/2` was split on its last two segments and indexed as type `_history`, id `2` (finding 18); relative `Patient/123/_history/2` was fine. The parser now takes the `/_history/[vid]` suffix off first, per the reference regex in R4B references.html "Literal References", and cuts the base URL at the LAST `/[type]/[id]`, so a base path that contains the type name (`http://example.org/Patient/fhir/Patient/123`) is no longer split at the first.
- **`_sort` on a string uses whole values; on a token, coded rows.** A name part is indexed one row per word so a search finds it by any word; the sort took the smallest of those, so family "Zeta Alpha" sorted as "alpha", before "Beta" (finding 19). A CodeableConcept's text is a row with an empty code for `:text`; the sort put those empty strings first, where R4B 3.1.1.5.1 says a resource with no value sorts last (finding 20). Both paths (SQL and general) now take string rows whose `param_index` is a multiple of 100, the whole-value convention now documented on `StringSearchParameters.paramIndex`, and token rows with a non-empty code. **Schema 9** moves Address and ContactPoint rows onto that convention and rebuilds the search index from the stored resources on upgrade (derived data; measured 2026-09-04 at 467s for the 5 GB MIMIC load).

- **Saving a resource scanned every index table (schema 8 fixes it).** The delete that precedes a save's re-index was one WHERE, `(type = ? AND id = ?) OR substr(id, 1, n) = ?`, the OR half there to remove the rows of anything the resource had contained. No index can serve that half, so every save read every index table, and the rate fell as they grew. Measured 2026-09-06 on the same 5,000 MIMIC resources with fhirant's `perf_load.dart`: published 0.12.0 **7.0s**; this package before the fix **30.2s**, the ProcedureED file at 110 resources/s against 1,409 on 0.12.0; the OR half removed, 7.3s (the cause, isolated). Now two deletes per table: the resource's own rows through the primary key, and the contained rows as a range on `id` (`>= '<type>/<id>#'`, `< '<type>/<id>$'`) among the `#`-typed rows, through a partial index on `id WHERE resource_type LIKE '#%'` per table (nine, empty on a database with no contained resources). The LIKE in the delete is literal SQL, not a bound parameter: SQLite applies a partial index only when the statement carries the same term, and the bound form measured 19.8s. With the fix: **7.7s**. `save_path_plan_test.dart` renders the DAO's own delete condition into EXPLAIN QUERY PLAN and fails on a SCAN. Schema 8 creates the indexes on an existing database.
- **Planner statistics follow the data.** The earlier fix ran ANALYZE on create, on upgrade, or when `sqlite_stat1` was missing. A database created empty and then loaded with 928,935 resources (measured 2026-09-06) carried statistics for three empty indexes and nothing else, because ANALYZE on empty tables writes no rows and it never ran again: `status=final AND code` took **58s** where the analysed database answered in 0.23s; ANALYZE afterwards took 5.9s and fixed every number. Now, as SQLite documents ("Automatically Running ANALYZE", read 2026-09-06): `PRAGMA optimize=0x10002` on every open and after every bulk save, which runs ANALYZE only for tables whose indexes lack statistics or that have grown or shrunk 10-fold (SQLite 3.46+; the bundled library is 3.53.4), and `PRAGMA analysis_limit=1000` so the ANALYZE it triggers is approximate and bounded. `optimizePlannerStatistics()` is public for a server's timer and shutdown. `planner_statistics_test.dart`: statistics appear after a bulk save into an empty database, and on opening a database that has data but none.
- **Not done: a sort-index walk for `status=final&_sort=-date`, measured and removed.** The idea was to read the sort key's index in value order and probe each row against the filter instead of grouping every match. On the 929k-resource MIMIC load with real statistics, interleaved twice on one build: `subject(48,554 records)&_sort=-date` **0.62s without, 8.05s with**; `status=final&_sort=-date` 8.9s without, 8.5s with; the 963-record patient 0.04s vs 0.10s. SQLite cannot walk `idx_date_value` in order while filtering on resource type and parameter without an index that leads with those columns, so the walk read far more than the estimate assumed. Removed before release. The 8.9s for `status=final&_sort=-date` stands as the open performance item (the ~1s recorded earlier was not reproduced on this database) and belongs to the index-design review with the composite-index question.
- **`SearchParameterDefinition.targets`.** A reference parameter's declared target types (`SearchParameter.target`, read from search-parameters.json), sorted; empty for other types and for the reference parameters whose definition declares none. What `_include=[type]:[parameter]:[target]` may name and what a CapabilityStatement's `searchRevInclude` is derived from. `fhir_generator/bin/regen_search_parameter_types.dart` regenerates this file alone.
- **`referenceTargets` for `_include`.** `FhirDao.referenceTargets(type, ids, parameter:, targetType:)` returns the `(type, id)` targets a reference search parameter points at on the given resources, from the reference index, every reference parameter for `*`. R4B search.html 3.1.1.5.4 (read whole): "Both _include and _revinclude are based on search parameters, rather than paths in the resource". fhirant had walked the resource JSON for a key named like the parameter, so `Observation:patient` (element `subject`) found nothing. An identifier-only reference has no target; an absolute reference under a base other than `serverBaseUrl` is another server's and is left out (admitted when the base is unknown, as the reference search does). Ids are chunked at 500 per statement.
- **Compartment search is a search.** `FhirDao.search` and `searchCount` take a `CompartmentScope('Patient', '123')`, and `Patient/123/Observation?code=…` is one SQL condition on the reference index ANDed with the query (R4B search.html 3.1.1.2, compartment context), paged and sorted like any other search. Which parameters put a type in a compartment comes from the published CompartmentDefinitions (`compartment_definitions.dart`, generated from profiles-resources.json by `fhir_generator/bin/regen_compartments.dart`; R5's `{def}` placeholder is dropped). The focal resource is in its own compartment, together with any of its type pointing at it (a Patient through another's `link`). A type the compartment does not include, or an unknown compartment, is an empty result and a count of 0. `compartmentMembers(scope, types:, since:)` lists every member by type for `$everything` and export, one indexed query per type. Before this, fhirant kept its own hand-written path list and passed every compartment id back in as `_id`, so a patient with 48,554 Observations was a 48,554-value IN list and the compartment total ignored the query.
- **`InsurancePlan?name=` is indexed.** Its expression is `name | alias`, with no resource prefix, and the generator dropped it silently; it was the one R4 search parameter with no extractor row. Generator `8b1f1ed`.
- **A search returning one page no longer reads every match.** `search` hydrated every matching id — one query and one parse each — built the whole list in memory and then discarded all but the page. The ids are now sorted and cut to the requested page BEFORE any resource is read. Measured on 928,935 MIMIC-IV-on-FHIR resources, `Observation?status=final` with `count: 20` over 813,513 matches: **174.58s → 12.68s**.
- **Paging is stable.** The matching ids were a `Set`, whose iteration order is undefined, so offset 20 was not guaranteed to continue where offset 0 stopped. They are sorted before paging.
- **`searchCount` no longer reads any resource.** It called `search` with no count and returned `results.length`, so counting 813,513 matches parsed all 813,513 resources. The id resolution is its own method now and counting uses that: **217.94s → 10.52s**.
- **Only the id column is read from the index tables**, not every column of every matching row. Selecting whole rows marshalled searchPath, searchName, values, paramIndex and lastUpdated for each of 813,513 matches to keep one string. Converted for token, string, date, number, quantity and uri. Measured on the same 928,935 resources, warm: token search **12.68s → 5.97s**, count **10.52s → 6.25s**, a date search **48.28s → 5.34s** against the published 0.12.0.
- **The value indexes are created by this package.** Every search table's primary key is `(resource_type, id, search_path, search_name, param_index)`, whose leading columns are what a search produces, not what it filters on, and this package created no index on any value column. fhirant had created them itself since its first schema, so it never showed the problem; any other consumer got a full scan per resource type on every search. Twelve indexes now, one per value column, including one on `quantity_value` that fhirant's list never had.
- **The database is ANALYZEd when it has no statistics.** Without `sqlite_stat1` the planner guessed, and on a 5 GB database it chose the primary key for a `SELECT DISTINCT id … WHERE reference_id_part = ?`, whose leading column matched 2.9 million rows: 0.01s became 10.35s. With statistics the same query is 0.00s. `ensurePlannerStatistics` runs on create, on upgrade, or when the table is missing. **It and `createValueIndexes` are public** because a subclass that overrides `migration` — fhirant does — replaces `beforeOpen` and `onUpgrade` wholesale and has to call them itself.
- **The page is cut in SQL for a single token parameter.** `status=final` alone, with `_count=20`, used to have SQLite hand every one of 813,513 ids to Dart so Dart could keep 20. For one plain token parameter — one repetition, no modifier, no comma, no `_has`, no `_sort` — the resolver now runs `ORDER BY id LIMIT count OFFSET offset` itself. Measured on 928,935 resources, warm: **5.13s → 1.19s**, of which 0.55s is SQLite finding the page and the rest is reading 20 resources. Every other shape still takes the general path; widening this to several parameters means `INTERSECT` across the index tables.
- **Several token parameters page in SQL too.** Each further plain token parameter becomes `id IN (SELECT id … WHERE …)` on the first one's select, through Drift's `isInQuery`, so SQLite intersects the parameters and stops at the page. Four tests pin stable paging, intersection rather than union (a mutation to union fails with the exact wrong rows), and agreement with the general path. `status=final AND code=227969`, 20 rows: **0.73s** on a clean machine, faster than the single parameter's 1.12s because the intersection narrows the set before the page is cut. (A first reading of 2.10s was taken under a load average of 7.3 from an unrelated process, with every query on that run doubled; the clean re-run attributes the figure.)
- **Date parameters page in SQL, alone or with tokens.** The date WHERE is a builder now (`_dateCondition`), and the SQL-paged path takes any mix of token and date parameters, each nested on its own index table. `Observation?date=gt2100-01-01`, 20 rows: **4.80s → 0.02s**, with the token figures unchanged on the same run as the control. That value matches nothing, which is the case an index wins outright; a value matching a quarter of the table costs what it costs. Three tests: date paging with the prefix honoured, a token and a date intersecting across two tables, and a non-date falling back.
- **String parameters page in SQL.** The default starts-with match is a builder (`_stringCondition`); `:exact` and `:contains` still take the general path. `Observation?value-string=no`, ~39,000 matches, 20 rows: **0.94s → 0.01s**, A/B by stashing the builder, token control unchanged. Three tests: starts-with not contains, string ∩ token, and a modifier falling back.
- **Reference, number, quantity and uri parameters page in SQL.** Each is a builder now (`_referenceCondition`, `_numberCondition`, `_quantityCondition`, `_uriCondition`), so every parameter type except composite and special pages in SQL and intersects with the others there. A/B against a worktree of the previous commit, interleaved twice under a load average of 4–5 (the unchanged `status=final` query moved 1.5–2.6s between runs on both arms, which is the noise band): `subject=Patient/…&code=227969`, one patient's 48,554 Observations against a code with 19,330, 20 rows: **0.72s / 0.44s → 0.08s / 0.12s**. `value-quantity=gt100`, 50,030 of 366,433 rows, 20 rows: **2.13s / 2.24s → 0.01s / 0.01s**. Number and uri have no rows in the MIMIC data, so they are pinned by tests only.
- **A quantity value in the specification's own form matched nothing.** R4B 3.1.1.4.11 writes it `[prefix][number]|[system]|[code]` — its example is `value-quantity=5.4|http://unitsofmeasure.org|mg`. This package read a three-part value as `system|number|code`, so the URL was parsed as the number, failed, and the search returned an empty set. Measured: `value-quantity=gt100|<system>|mg/dL` returned **0 rows** where 4,098 match; it returns them now. The two-part form that used to be accepted (`5|mg`) is not one the section defines and is no longer read; `5.4||mg` matches "either the code or the stated human unit", as the section says. A consumer whose tests assert the old `system|number|code` order (fhirant's `search_test.dart` does) will see them fail, correctly.
- **`eq`, `ne`, `sa`, `eb` and `ap` on number and quantity follow R4B 3.1.1.4.5–6.** A search number has an implicit range, half a unit of its last significant digit either side: `100` is [99.5, 100.5), `100.00` is [99.995, 100.005), `5.4` is [5.35, 5.45). `eq` ("the range of the search value fully contains the range of the target value") was exact equality, so `probability=0.3` did not find 0.31; `ne` was its complement; `sa` and `eb` were not handled at all and fell into `eq`, which is a wrong answer for both. `gt`/`lt`/`ge`/`le` stay exact, as the text says ("the implicit precision of the number is ignored"). `ap` is the range widened by the recommended 10%. The bounds are built as decimal strings and parsed, not as `value ± half` in floating point: `5.4 - 0.05` is 5.3500000000000005, which would have put a stored 5.35 outside the range that contains it. `implicitRange` is exported. One example in 3.1.1.4.6 (`1e2` as [95, 105), "1 significant figure") contradicts the rule as worded and is not followed; HAPI matches `eq` exactly by a recorded decision with the spec editor and Microsoft's server widens by the last decimal place, so neither follows the text either — the text is what is implemented, and the deviation from both is documented at `_numericPrefixCondition`.
- **Date search follows R4B §3.1.1.4.7: every value is a range, and Period and Timing values are indexed.** Three defects, found together on the 928,935-resource MIMIC-IV load. (1) A Period-valued date parameter wrote **no index row at all** — the extractor handled date, dateTime and instant and returned nothing for anything else — so `Encounter?date=…` (Encounter.period), every `effectivePeriod` and `performedPeriod` silently returned nothing: 637 Encounters, zero `Encounter.date` rows. (2) `eq` was equality on one stored instant, so `date=2013-01-14` matched only a value at exactly midnight and `date=2013` only New Year's; the section says "the date 2013-01-10 specifies all the time from 00:00 on 10-Jan 2013 to immediately before 00:00 on 11-Jan 2013". `ne` was its complement, `sa`/`eb` were `gt`/`lt`, and `ap` was ±1 day. (3) An explicit offset was discarded on the way in (fixed in `fhir_r4` itself, same release). Now every row is `[date_value, date_value_end)`: a date or dateTime covers one unit of its own precision, a Period runs from its start to the end of its end value's own range, with a missing bound stored as null ("a missing lower boundary is 'less than' any actual date. A missing upper boundary is 'greater than' any actual date"), and a Timing by "the outer limits" of its events and bounds period. The search value gets the same range, and the prefixes are the §3.1.1.4.5 range rules — every worked example in §3.1.1.4.7 is a test, including the three open-ended Periods under `ge`, `le`, `sa` and `eb`. `_lastUpdated` goes through the same rule. The search-value grammar is checked whole before parsing: `2013-1-4` used to parse as the year 2013. The date index is rebuilt from the stored resources on upgrade (see the schema entry below); 907,477 → 921,632 rows. Measured after: `Observation?date=2116-12` **0 rows → 20 rows, 0.00s**; `Encounter?date=ge2110` **0 → 20, 0.01s**; `date=2137&status=final` 0 → 20 rows at 2.17s, which is the nested `status` subquery over 813,513 rows being materialised — the same query with `status` first is 0.6s, so the order of the parameters decides the outer select and that is the next thing to fix.
- **A multi-parameter search picks its outer select by size.** SQLite cannot: `sqlite_stat1` holds one average per index (`idx_token_value`: 25 rows per value) and this build has no STAT4, so the planner reads `status=final` as 25 rows when it is 813,513 and always walks it through the value index followed by a sort that must see every row before the `LIMIT`. Each parameter is now probed for its row count — `SELECT count(*) FROM (SELECT id … LIMIT n)`, counted inside SQLite, escalating 2,000 then 100,000 so the common case costs a few milliseconds — and the smallest set is the outer select; a nested set known to be small is materialised (`id IN (SELECT …)`), one that is not is a correlated `EXISTS` on an alias of its table, whose cost is the outer's size rather than the inner's. When every set exceeds the cap the parameters are taken in the order given with `IN`, as before. Measured on the MIMIC load, 20 rows, A/B interleaved twice: `status=final&code=227969` **0.64s → 0.23s**; `date=2137&status=final` **2.39s → 0.21s**; `subject=<963-record patient>&code` **0.10s → 0.01s**; `subject=<48,554-record patient>&code` **0.06s → 0.20s** — the one regression, a patient with more records than the second probe stage resolves cheaply, paid for by the probes themselves. A single-parameter search is not probed and is unchanged.
- **A sorted search pages in SQL, and a sort over more than ~32,000 matches no longer throws.** `_sort` used to read every matching resource, then look up each key with `id IN (<every id>)`, which SQLite caps at 32,766 variables: measured on the MIMIC load, `Observation?subject=<48,554-record patient>&_sort=-date` **threw `too many SQL variables`**, and `status=final&_sort=-date` would have read 813,513 resources first. Now each sort key is a `LEFT JOIN` to its index table with `GROUP BY id`, ordered by `MIN` of the value ascending or `MAX` descending — §3.1.1.5.1, "the sort is based on the item in the set of multiple parameters that comes earliest in the specified sort order" (the old code took `param_index = 0`, whichever value was extracted first) — `NULLS LAST` (SQLite's default for ascending is nulls first), tie-break on id, `LIMIT` in the statement. A string sorts on its normalized column, so case-insensitively as the section SHOULDs. Numbers and dates compare as themselves (the old lookup compared `numberValue.toString()`). Measured, 20 rows: `subject=<963-record patient>&_sort=-date` **0.18s → 0.01s**; the 48,554-record patient **crash → 0.34s**; `status=final&_sort=-date` **6.2s** (813,513 join probes; the previous path was not measurable). The general path's sort — reached only for a search with a modifier, chain, `_has` or comma — derives its keys from the resources through the same extractor that writes the index, so it has no variable limit and the same earliest-value semantics; a test drives every sort case through both paths. A search with no parameter at all (`Observation?_count=20`) pages in SQL from the resources table.
- **A comma (OR) and a repeated parameter (AND) page in SQL.** The SQL-paged path refused both and fell back to reading every match. Each repetition is one condition on its own aliased table; the comma-separated values inside it are ORed on that table, split with FHIR's backslash escaping so `a\,b` stays one value. `FhirDao.lastSearchPagedInSql` (`@visibleForTesting`) says which path a search took, and every paged test now asserts it: a right answer alone proves nothing about the path.
- **Modifiers page in SQL.** `:missing` on every type (`true` as `NOT EXISTS`, `false` as `EXISTS`; a search made only of negated conditions selects from the resources table), string `:exact` and `:contains`, token `:not`, `:text`, `:in` and `:not-in` (an OR over the ValueSet's codes; `:not-in` with an empty expansion excludes nothing), reference `:identifier` and the type modifier (`subject:Patient=23`), uri `:below`. Still on the general path: `:of-type` (the index has no identifier type) and uri `:above` (the stored value as a prefix of the search value). Each modifier has a test that asserts the path taken.
- **`_tag`, `_security`, `_profile` and `_source` are indexed, and `_id` and `_lastUpdated` page in SQL.** The four meta parameters are published against Resource, which the generated extractor's per-type switch could never name, so no index row was ever written for them and the DAO answered them by decoding every stored resource of the type in Dart: measured, `Observation?_profile=<mimic-observation-labevents>` on the 929k-resource MIMIC load took **13.6s**; now **0.08s**, and with `status=final` 0.23s. The extractor writes them on save (generator `dfcab53`), they take the ordinary token and uri builders, and the upgrade fills them in for stored resources (see the schema entry below). `_id` and `_lastUpdated` are conditions on the resources table itself, so both combine with any other parameter in one statement. `searchParameterFor` falls back to the DomainResource and Resource definitions, which is where R4B 3.1.1.4.1's parameters live.
- **A reference searched by absolute or canonical URL works.** R4B 3.1.1.4.12's `[parameter]=[url]` form: the general path added no condition at all for a value containing a URL, so `subject=http://server/Patient/23` returned every resource that had a subject, and the SQL path compared the whole URL to the id part and matched nothing. Both now match the stored reference as written; a bare `[url]` also matches `[url]|[version]` (R5 3.2.1.6.1.5 reads the `|version` as the business version), and `Type/id` continues to match an absolute reference to that type and id. The prefix test uses `substr`, not `LIKE`, because `_` is a LIKE wildcard and common in URLs.
- **Chains and `_has` run in SQL, and every search the SQL path can express is resolved there whether or not it pages.** A chain (`subject.name=peter`, `subject:Patient.name`, `subject.organization.name`) is a condition on the reference table whose target is a resource satisfying the rest of the chain: the target set is probed and either materialised (`IN`) or tested by correlated `EXISTS`, the same rule as everywhere else, one hop at a time, ORed across every resource type that declares the chained parameter when no type is given. `_has` is a condition on the target type's reference table whose "id" is the referenced id. The general path did a chain by reading every reference row for the parameter and running a full search on the target for each one, and did `_has` without regard to its reference parameter (any reference from the target type to the source counted) after hydrating every matching target. Measured on the MIMIC load, load average ~5: `Observation?subject.gender=female&code=227969` **killed at 600s → 0.61s**; `Patient?_has:Observation:subject:code=227969` **3.8s → 0.48s**. A search with no `_count` now runs the same SQL without a `LIMIT`, and `searchCount` counts that; the Dart set arithmetic remains only for `:of-type`, uri `:above`, composite and special parameters. A constrained chain to a type that lacks the parameter (`subject:Group.family`) matches nothing rather than falling back.
- **`CodeableConcept.text` is indexed as a display, not as a code.** R4B 3.1.1.4.4: `:text` "does a partial searches on the text portion of a CodeableConcept or the display portion of a Coding", "instead of the default search which uses codes". The text was written as the token value, so `code=Heart Rate` matched a CodeableConcept by its text and `code:text=heart` could not find it. Both corrected; a text-only CodeableConcept still counts as present for `:missing=false`.
- **Modifiers this package does not implement are refused.** R4B 3.1.1.4.4: "Server SHALL reject any search request that contains … a modifier that the server does not support for that parameter … using an HTTP 400". Token `:above`/`:below` (code subsumption, 3.1.1.4.10) and reference `:above`/`:below` (resource hierarchies, 3.1.1.4.14) were listed as allowed and answered as a plain match, a silently narrower answer. They throw `UnsupportedSearchModifier` now, with a message saying the modifier is defined but unsupported here. Both checks run before anything is built, on either path.
- **Schema 6 → 7 is one step: the whole search index is rebuilt from the stored resources.** The index is derived data, and everything this release changed about it (value as written for `:exact`, dates as ranges, Period and Timing rows, the meta parameters, text as display, value indexes) comes back from one re-extraction. `rebuildSearchIndex()` is public for a subclass that overrides `migration` (fhirant) and is the right call after any change to the generated extractor. Measured: **467s for 928,935 resources** under a load average of ~5.5; date rows 907,477 → 921,632, uri rows 0 → 928,935 (the profiles); `Encounter?date=ge2110` and `Observation?_profile=…` both 0 rows before and 20 rows in 0.0s after.
- **Sixty-odd parameters that indexed nothing.** Measured by saving a resource and reading the index tables: a token parameter on a ContactPoint (`Patient?phone=`, `telecom`, `email`: 20 parameters) or an id (ImagingStudy `series`) wrote no row, nor did a quantity parameter on a Money or a Range, a reference parameter on a uri element, or either half of an R4B CodeableReference, and the 35 `relatedArtifact.where(type=…).resource` parameters (`composed-of`, `depends-on`, `derived-from`, `predecessor`, `successor` on every definitional resource) had the generated extractor filter the canonicals for `RelatedArtifact`, so they wrote nothing either (generator fix). All write rows now, per R4B 3.1.1.9's cross-map of parameter types to data types.
- **Number and quantity rows are ranges, as the specification says stored values are.** R4B 3.1.1.4.5: "Searches are always performed on values that are implicitly or explicitly a range" — a decimal written `2.0` covers 1.95–2.05, an integer is a point, a Range is its explicit bounds with either open. The comparison rules are applied to both ranges: `eq` is containment, `gt`/`lt` are overlap with the region above/below the search value, `sa`/`eb` are disjoint-and-beyond, `ap` is overlap widened by 10%. Two consequences worth knowing: a decimal written `100.0` matches `gt100` (its range reaches above 100), which servers that compare points do not do; and a search more precise than the record (`0.30` against a stored `0.3`) finds nothing, as the containment rule says. JSON number parsing drops trailing zeros, so a record can be no more precise than its shortest spelling. Schema 7 carries the new columns; the rebuild fills them.
- **References: the server base, ambiguous bare ids, canonical `:below`, mime-type `:below`.** R4B 3.1.1.4.12: "A relative reference resolving to the same value as a specified absolute URL, or vice versa, qualifies as a match" — `FhirDao.serverBaseUrl`, set by the server, makes `subject=Patient/123` and `subject=<base>/Patient/123` match each other and exclude another server's `…/Patient/123`; unset, a relative search admits any absolute reference with that type and id. "Servers SHOULD reject a search where the logical id refers to more than one matching resource across different types": `subject=23` throws `AmbiguousReference` when 23 is both a Patient and a Group here (one indexed count; it used to match both). 3.1.1.4.13: `:below` on a canonical reference controls the version — `depends-on:below=http://acme.com/p` matches `|1.0`, `|1.1`, `|2.0` and `…|1` the first two. 3.1.1.4.10.1: `contenttype:below=text/xml` finds `text/xml; charset=UTF-8`; `:below` on a code (subsumption) or on a resource hierarchy (`location:below=42`, 3.1.1.4.14) stays refused.
- **Escaping, `_has` OR values, `_list`, `_text`, `_content`.** R4B 3.1.1.4.19: each split now consumes only its own separator's escape, so `code=a\|b` is the single code `a|b` (the comma split used to strip the `\|` first and the pipe split then read system `a`, code `b`), and an illegal escape (`xx\xx`) is `InvalidSearchValue`. 3.1.1.4.16: `_has:Observation:patient:code=123,456` is an OR (it was one literal value). 3.1.1.4.22: `_list=42` selects the resources List/42's `entry.item` references, from the List's own index rows, and combines with other criteria; a functional list (`$current-allergies`) is refused rather than answered with everything. 3.1.1.4.20: `_text` searches the narrative (indexed as a string row, tags stripped, folded) and `_content` the stored resource, every word of the value having to appear; both used to be ignored, which answered with every resource. Neither is the full-text engine the section SHOULDs (no OR, thesaurus or proximity).
- **Composite parameters work.** R4B 3.1.1.4.17. The composite extractor was a stub that wrote nothing, and the resolver guessed the components by splitting the parameter NAME on `-` (`code-value-quantity` → `code`, `value`, `quantity`) and intersected resource-level matches, so every composite search was wrong or empty. The generated definitions now carry each composite's components (the type of the parameter each stands for, and its expression relative to the composite's element, e.g. `code` and `value.as(Quantity)` on `Observation.component`); the extractor evaluates them on that element and writes one row per combination of their values, each component in a typed slot, so a `$`-joined value is matched against values on the SAME element — "a combination of key/value, not an intersection of separate matches". Each slot applies its own type's rules (the token forms, quantity prefixes with system and code, dates as ranges). OR of sequences by comma; a value with the wrong number of parts is an error; modifiers stay refused. The section's examples are the tests: `component-code-value-quantity=http://loinc.org|8480-6$lt60` does not match a 55 sitting on the diastolic component, `characteristic-value=gender$mixed,owner$true`, `context-type-value=focus$…`, and `result.code-value-quantity=…` through a chain.
- **`Location?near=` works.** The special extractor was a stub and nothing resolved `near`, so it found nothing. `[latitude]|[longitude]|[distance]|[units]`, km when the units are omitted, 10 km when the distance is (the definition leaves that to the server; this is the number chosen), `m` and miles accepted. The distance is the equirectangular approximation computed in SQL — this SQLite build has no trigonometric functions — which the definition permits ("various techniques that might have differing accuracies").
- `:text` on a token also searches `Identifier.type.text`, the third place 3.1.1.4.10 names.
- **Contained resources are indexed, and chains search inside them.** R4B 3.1.1.5.5: "A chained condition will be evaluated inside contained resources", and "By default, search results only include resources that are not contained". Contained resources were not indexed at all, so `Observation?subject.name=Smith` with the patient in `contained` found nothing and `Observation?subject=#p1` matched nothing. Each contained resource is now indexed under `#Type` with its container's id, a container's `#id` references point at those rows, and a chain looks in both the referenced type and `#Type`. Contained resources are never returned as matches in their own right.
- **`searchCount` is one `count(DISTINCT id)` in SQL.** It fetched every matching id and counted the list: 813,513 matches took 4.4–9s and is now 1.34–1.40s on the same load.
- **A date, number or quantity containment bounds the low column on both sides.** `date=2137` was `low >= 2137 AND high < 2138`, which is correct but, once the planner had statistics, made it walk the `date_value_end` index and then filter: 0.21s → 4.29s after `ANALYZE`. `low < 2138` is implied and is now stated, so the planner uses the `date_value` range.
- **A search whose every part is a fair share of the type walks the resources table.** `Observation?date=2137&status=final` (60,056 and 813,513 of 813,540 Observations) sorted the 60k date rows and ran the status `EXISTS` on each, 1.85s on its own and 3.82s under load. The expected walk to fill a page is `(count + offset) / Π(size / total)`; when that is shorter than the smallest part's set, the query walks `resources` in primary-key order with every part nested as `EXISTS`, and stops at the page. A/B against the same tree with only the walk disabled, interleaved twice: **1.12s → 0.31s**, `subject=X&code=Y` 0.44s → 0.30s, the `subject.gender=female` chain 0.59s → 0.46s; an unchanged query moved 0.67s → 0.66s. `code=X` (2,000) with `status=final` expects an 8,000-row walk and keeps the 2,000-row outer.
- **Which token parameters are mime types comes from the definitions.** `:below` on a mime-type parameter was admitted by the shape of the value (a `/`), so `code:below=text/plain` was answered as a prefix match when it is subsumption. The generator now reads the StructureDefinitions and marks the token parameters whose element is bound to the mimetypes value set (`format`, `contenttype`, `content-type`, `payload`); `:below` on any other token is refused.
- **`:text` on a token is a string search: starts-with, case- and accent-insensitive.** R4B 3.1.1.4.10: "the search functions as a normal string search", and 3.1.1.4.8 defines that as equals-or-starts-with after normalization; R5 spells it out for this modifier (`code:text=headache` matches codes "that start with or equal the string 'headache' (case-insensitive)"). It was `LIKE %value%`: wider than asked (`code:text=pressure` found "Blood Pressure") and case-folded for ASCII only, so `cephalee` could not find "Céphalée". The display is now stored normalized in `token_display` (the index is rebuilt by the schema step).
- `Observation?status=final&_sort=-date` at 6.2s is 813,513 primary-key probes for the join. Driving the query from the sort key's own index would stop at the page, and is the next thing to try for a sort over a large set. That, and resolving the ids in Dart rather than in SQL, are what the remaining ~10s is.

## [0.12.0]

- **A save that cannot be indexed now fails instead of succeeding quietly.** `_updateSearchParameters` caught every exception, printed it and returned `false`, and `saveResource` ignored that `false` and returned the resource. A record could therefore be stored with no index rows while the caller was told the save had worked, and it was then invisible to every search — a wrong answer rather than an error. The failure propagates now.
- **`saveResource` writes the resource, its history row and its index rows in one transaction**, so a failure part way through leaves the store as it was rather than leaving a resource nothing can find. A failed update keeps the previous version.
- `FhirDao.extractSearchParameters` is a `@visibleForTesting` field holding the generated extractor, which is what lets a test make indexing fail. Production behaviour is unchanged.

## [0.11.0]

- **A repeated search parameter is an AND, and a comma is an OR.** R4 3.1.1.4.17 gives the two separators different meanings: `?given=Anna&given=Beth` asks for records having *both*, `?given=Anna,Beth` for records having *either*. Every value handed to `search` was previously treated as one OR group, so the AND form returned the OR answer. Each element of a parameter's value list is now one repetition, and the elements are intersected; the comma split happens inside each element, where FHIR's escaping applies, so `name=Clinic\, North` stays a single value rather than becoming two.
- The comma split belongs here rather than in a caller: it needs the escaping rules and the parameter's declared type, and a caller that splits first turns an OR into an AND with no way for this package to tell the difference.

## [0.10.0]

- **Search modifiers and comparators now work.** They were read off the END of the value (`family=Smith:exact`, `birthdate=1980-01-01:gt`), a syntax FHIR does not have, so every modifier and every comparator was unreachable from a conforming client. Measured through a REST server before and after: 7 of 41 queries returned anything, now all 41 do. The modifier is taken from the parameter name and the comparator from the front of the value, as the specification defines them.
- A search parameter is now dispatched on its **declared type**, read from the published SearchParameter definitions and generated into `search_parameter_types.dart`. Nothing is inferred from the shape of a value any more, so a name beginning with a comparator's two letters — Apgar, Nelson, Ledger — is no longer mistaken for one. Comparators come from each parameter's own `comparator` element, so a custom parameter that narrows the set is honoured.
- A key is split at the first `.` or `:` and the remainder carried whole, which is how chained (`subject:Patient.name`) and reverse-chained (`_has:Observation:patient:code`) parameters are parsed without guessing what a colon means.
- **FHIR's escaping is honoured.** `$`, `,` and `|` inside a value are written with a leading backslash, and were previously split on regardless: `Organization?name=Clinic: SOUTH Wing` returned `Clinic: North Wing`. Values are no longer truncated at a colon, and `code=a\,b` is one code.
- **`:exact` is exact, and accents fold.** Strings are indexed twice: normalized for the default and `:contains` searches, verbatim for `:exact`. Folding covers accents as well as case, so `family=Munoz` finds `Muñoz` and `family:exact=munoz` no longer matches `Munoz`. **Schema version 5 to 6**; the string index is rebuilt from the stored resources on open, so nothing is left half-indexed.
- `eq` and `ne` were missing entirely from date, quantity and number comparators.
- `:missing` answers both `true` and `false`. `:identifier` on a reference tests `Reference.identifier` rather than the referenced resource. `:above` and `:below` on a uri are reachable. `subject:Patient=23` behaves as `subject=Patient/23`.
- An unsupported modifier now throws `UnsupportedSearchModifier` instead of being ignored, which R4 3.1.1.4.4 makes a SHALL: ignoring one silently changes what a query means. An unknown *parameter* is still ignored, as the same page says it should be.
- The search parsing API is exported so a server can catch that failure and return the 400 the specification requires.
